# 5. Security and secrets management

## Secret storage

The database password is **generated by CloudFormation inside Secrets
Manager** (`GenerateSecretString`) and never leaves AWS. It is not in Git, not
in a parameter file, not in the CloudFormation console, and no human ever sees
it. `AWS::SecretsManager::SecretTargetAttachment` then writes the host, port,
database name and engine back into the same secret, so the application needs
exactly one ARN.

## How each deployment style consumes it

| Style | Mechanism | Result |
|---|---|---|
| ECS Fargate | `secrets` block in the task definition, `valueFrom: <arn>:password::` | The ECS agent (task execution role) resolves the value and injects it as an environment variable. The application never calls Secrets Manager. |
| EC2 | Instance role + `DB_SECRET_ARN` in `/etc/app.env` | The app fetches the secret with boto3 at start-up using the instance role. No credentials on disk; `/etc/app.env` holds only an ARN. |

Rotating the secret therefore means: rotate in Secrets Manager, then restart
the tasks/services. No code change, no redeployment of infrastructure.

## Access control

* **CI to AWS**: GitHub OIDC federation, short-lived credentials, trust policy
  restricted to this repository. No long-lived access keys exist anywhere.
* **Task execution role**: pull images + read *only* the one database secret.
* **Task role** (application identity): read that secret, write its own logs.
  Nothing else.
* **Instance role**: read the artifact bucket, the CodeDeploy agent bucket and
  the database secret; plus `AmazonSSMManagedInstanceCore` so operators use
  Session Manager instead of SSH keys.
* **Security groups**: the database accepts 5432 only from the ECS and EC2
  security groups. Application ports 3000/8000 accept traffic only from the
  ALB security group. Nothing accepts traffic from `0.0.0.0/0` except the two
  load balancers on 80/443.

## Data protection

* RDS storage encrypted (`StorageEncrypted: true`), not publicly accessible,
  in subnets with no route to the internet.
* EBS volumes on EC2 encrypted.
* S3 artifact bucket: SSE-AES256, versioning on, all public access blocked.
* IMDSv2 enforced on EC2 (`HttpTokens: required`) to prevent SSRF credential
  theft.
* ECR scan-on-push flags vulnerable base images.

## What to add before a real production launch

1. ACM certificate + HTTPS listener on 443, HTTP redirected to HTTPS.
2. AWS WAF web ACL on both load balancers.
3. Secrets Manager automatic rotation with the RDS rotation Lambda.
4. Replace `PowerUserAccess` on the CI role with a policy scoped to the exact
   services and resource ARNs this project touches.
5. GuardDuty, AWS Config rules and CloudTrail organisation trail.
